# 0004. Один черновик реализации на заказ

- Статус: принято
- Дата: 2026-09-13

## Контекст

После печати в 1С пишется черновик реализации по заказу, и нужно убедиться, что он действительно записался. Автор задания в переписке подтвердил: механизм защиты от дублей обязателен.

Факты с живой базы, 2026-09-13:

1. Примерно раз в 30 запросов 1С отвечает `503`. Если такое случилось на POST, снаружи не отличить «документ не создан» от «создан, но ответ потерялся».
2. POST реализации **игнорирует переданный `Ref_Key`**: отправили `60e9c84d-…`, 1С создала документ `5abb9f85-…`, GET по нашему ключу вернул 404.
3. **Повторный POST создаёт дубль**: появились 00УТ-000201 и 00УТ-000202 с одинаковым содержимым.
4. PATCH с `DeletionMark: true` отвечает 200, но пометку не ставит: лишний документ через API не убрать.
5. `$filter=ЗаказКлиента_Key eq guid'…'` работает, `substringof` по комментарию — ответ 400.
6. База общая: по заказу 00ДМ-000101 уже лежит черновик другого кандидата.

## Варианты

- **Клиентский `Ref_Key` как ключ идемпотентности.** Штатный для 1С способ, но эмулятор его не поддерживает (факт 2).
- **Ключ на каждое нажатие кнопки.** Повторы одного запроса не дублируются, но каждая новая печать того же заказа создаёт ещё один черновик. Для 1С это дубль реализации по одному заказу.
- **Один черновик на заказ: маркер заказа в комментарии, поиск перед созданием.** Повторная печать и повторы после сбоя возвращают тот же черновик.

## Решение

Черновик помечается маркером `[pickup-service заказ <Ref_Key заказа>]` в поле `Комментарий`. Данных получателя в маркере нет.

Запись (`PUT /api/v1/orders/{orderRef}/shipment-draft`) устроена так:

1. Читаем все реализации с `ЗаказКлиента_Key = заказ`, листая страницы до конца, и ищем среди них свою: с маркером и без пометки на удаление (`shipment.FindOurs`).
2. Нашли — возвращаем `200` и не создаём новую.
3. Не нашли — POST.
4. **POST ответил `503`, таймаутом или обрывом** — исход неизвестен. Повторного POST не делаем, возвращаемся к шагу 1: если документ всё-таки создался, он найдётся.
5. POST ответил `429` — запрос отклонён до обработки, после паузы повтор безопасен.
6. POST ответил `4xx` — 1С отказала по существу, не повторяем, отдаём `SHIPMENT_REJECTED` с текстом 1С.
7. После записи перечитываем документ GET по `Ref_Key`, выданному 1С, и сверяем заказ, маркер, число строк и по каждой строке товар, количество, цену, ставку и суммы (`shipment.Verify`). Расхождение — `SHIPMENT_NOT_CONFIRMED` со списком расхождений.
8. Два одновременных вызова по одному заказу внутри процесса сериализуются мьютексом на заказ.

## Последствия

- Сколько раз ни нажать «Отметить в 1С» и сколько раз ни повторить после сбоя, черновик по заказу один. Это проверяют тесты сценария и e2e на моке, где мок создаёт документ и отвечает `503`.
- Проверка записи отвечает на пункт задания «убедитесь, что он действительно записался»: мы не верим коду 201, а сверяем то, что реально лежит в 1С.
- Если кто-то пометит наш черновик на удаление, следующая печать создаст новый: отметки о выдаче больше нет, и это правильно.
- **Остаточный риск:** мьютекс работает внутри одного процесса. Два экземпляра сервиса одновременно могут создать два черновика: оба не найдут существующий и оба сделают POST. Для одного склада с одним сервисом это приемлемо; при горизонтальном масштабировании понадобится блокировка на стороне 1С или общая БД.
- Тестовые документы 00УТ-000201 и 00УТ-000202, созданные при проверке эмулятора, остались в общей базе: удалить их через API нельзя (факт 4).
