# 0009. Без кэша между запросами

- Статус: принято
- Дата: 2026-09-13

## Контекст

Экран заказа — около 20 запросов к 1С, и каждый может получить `503` или `429`. Справочники (ставки НДС, номенклатура, склады, партнёры) меняются редко. Кэш напрашивается.

## Варианты

| За кэш | Против |
|---|---|
| меньше запросов: реже встречаем `503` и `429` | главный критерий оценки — «суммы до копейки»: ставка, изменённая в 1С, до конца TTL даст расхождение |
| при лежащей 1С можно показать хотя бы список заказов | проверяющий может сбросить базу, и кэш покажет то, чего уже нет |
| | TTL, инвалидация, выдача устаревшего при ошибке и схлопывание одинаковых запросов — это код и тесты, которые бьют по читаемости |
| | нагрузки нет: один кладовщик, а `503` и `429` уже гасят повторы и ограничитель частоты |

## Решение

Кэша между запросами нет. Каждая операция читает свежие данные.

Внутри одной операции данные грузятся пакетно: справочные объекты запрашиваются по ключам из заказа, каждый ключ один раз, а не на каждую строку. Размер запроса зависит от заказа, а не от размера справочников в базе.

Остатки особенно важно читать свежими: устаревший остаток опаснее, чем его отсутствие. Кладовщик пойдёт за товаром, которого уже нет.

## Последствия

- Документ всегда совпадает с тем, что сейчас в 1С.
- При лежащей 1С список заказов тоже недоступен. Страница показывает конкретную причину и время до повтора, форма и введённые данные при этом не теряются ([деградация](../flows/degradation.md)).
- Если нагрузка вырастет, кэш справочников с коротким TTL добавляется внутри `infrastructure/onec` за теми же портами, сценарии и домен не меняются. Остатки и заказы кэшировать не стоит и тогда.
