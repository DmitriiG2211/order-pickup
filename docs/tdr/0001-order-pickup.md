# TDR 0001. Выдача заказа клиенту со склада

- Статус: черновик, дополняется по мере реализации
- Дата: 2026-09-13

## 1. Контекст и цель

Клиент оформил заказ и приехал забирать. Кладовщик открывает заказ, смотрит, чем склад реально располагает, вводит данные того, кто получает товар, печатает документ на выдачу и отмечает выдачу в 1С черновиком реализации.

Сервис — одна страница и HTTP API поверх чужой 1С:УТ 11.5, опубликованной только через OData. Исходников и конфигуратора нет.

## 2. Требования

### Функциональные

| # | Требование | Где реализовано |
|---|---|---|
| F1 | Состав заказа: артикул, наименование, количество, цена, ставка НДС, сумма, НДС, сумма с НДС, итоги | `GET /api/v1/orders/{orderRef}` |
| F2 | Остаток по каждой позиции на складе заказа | там же, [ADR 0003](../adr/README.md) |
| F3 | Поля получателя: фамилия, имя, отчество, телефон, почта | страница, `pickup.Receiver` |
| F4 | PDF: «Выдать» + ФИО в родительном падеже, телефон, почта, заказ, склад, таблица, итоги | `POST /api/v1/documents/pdf` |
| F5 | Тот же документ в JSON по контракту задания | `POST /api/documents/preview` (+ `/api/v1/...`) |
| F6 | После печати — черновик реализации в 1С и проверка, что он записался | `PUT /api/v1/orders/{orderRef}/shipment-draft` |
| F7 | Пол получателя по отчеству, если `gender` не пришёл | `person.GenderFromPatronymic` |

### Нефункциональные

| # | Требование | Как проверяем |
|---|---|---|
| N1 | Суммы сходятся до копейки: целые копейки, округление половины вверх, НДС от округлённой суммы строки, итоги из строк | unit-тесты на эталонах задания, live smoke |
| N2 | Ошибки 1С не роняют сервис, кладовщик видит конкретную причину | unit-тесты на подставных ответах 1С (503, 429, обрыв, зацикленная пагинация) |
| N3 | Учётная запись 1С не блокируется нашими действиями | тест: при неверном пароле клиент шлёт не больше одной попытки входа за время жизни процесса |
| N4 | Ошибка ввода показывает конкретное поле | тесты хендлера и сценария |
| N5 | Данные получателя нигде не сохраняются | тест логов, сигнатура записи черновика не принимает их |
| N6 | Запуск одной командой, порт 3000, адрес и пароль 1С из окружения | `docker compose up` на чистом клоне |

## 3. Ограничения чужой системы

Проверено на живой базе 2026-09-13, если не сказано иное.

| Поведение 1С | Что из этого следует |
|---|---|
| Страница ответа — 3 записи; `$top` игнорируется; признака обрезки нет | любую коллекцию читаем со `$skip` до пустой страницы |
| Сущность по ключу отдаёт табличную часть `Товары` целиком | строки заказа всё равно читаем коллекцией с пагинацией: на вложенной части не проверить, что она не обрезается |
| Примерно 1 запрос из 30 — `503` | повторы с паузой ([ADR 0007](../adr/README.md)) |
| При частых запросах — `429 «Превышена частота обращений к сервису»` (в задании не описано) | ограничитель частоты и пауза по `Retry-After` |
| Пять неудачных входов — блокировка на 5 минут, правильный пароль тоже не проходит (из задания, вживую не проверяли) | на 401/403 не повторяем, защёлка авторизации ([ADR 0008](../adr/README.md)) |
| POST реализации игнорирует переданный `Ref_Key` и выдаёт свой; повторный POST создаёт дубль | защита от дублей через маркер и поиск ([ADR 0004](../adr/README.md)) |
| PATCH с `DeletionMark: true` отвечает 200, но пометку не ставит | удалить свой тестовый документ через API нельзя |
| `$filter` по `ЗаказКлиента_Key eq guid'…'` работает, `substringof` — ответ 400 | маркер в комментарии ищем у себя после фильтра по заказу |
| База общая: чужие черновики видны, нумерация прыгает | «свой» черновик определяем по маркеру, а не по номеру или дате |
| В справочнике 9 ставок, среди них расчётные и нетиповая 13% | ставку берём из справочника по ключу строки ([ADR 0006](../adr/README.md)) |

## 4. Решение

Один Go-сервис на порту 3000 отдаёт страницу и JSON/PDF API. `httpapi` разбирает HTTP, `usecase` собирает сценарии, домен считает деньги и проверяет ввод, а `infrastructure/onec` изолирует OData-особенности чужой 1С. Данные получателя живут только в теле HTTP-запроса и документе в памяти; в реализацию 1С они не передаются.

Точка входа: `cmd/server`. Зависимости собираются руками: один `onec.Gateway` реализует чтение заказов, справочников, остатков и реализаций; PDF и склонение — отдельные адаптеры.

## 5. Потоки

1. Экран читает `GET /api/v1/orders`, затем выбранный заказ через `GET /api/v1/orders/{ref}`.
2. Preview и PDF сначала валидируют получателя, потом читают заказ и необходимые справочники. Ошибка формы не вызывает запросов к 1С.
3. После получения PDF страница вызывает `PUT /api/v1/orders/{ref}/shipment-draft`. Сценарий ищет свой черновик, при отсутствии создаёт его, затем перечитывает и сверяет строки.

## 6. Отказоустойчивость

GET повторяется при временной ошибке и таймауте; POST реализации не повторяется при неизвестном исходе. После такой ошибки сценарий снова ищет черновик по маркеру, поэтому не создаёт дубль. Клиент ограничивает частоту, уважает `Retry-After`, размыкает связь после серии сбоев и защёлкивает авторизацию после 401/403, чтобы не блокировать общую учётную запись.

## 7. Расчёты

Код: `internal/domain/money`, `internal/domain/vat`. Решения: [ADR 0005](../adr/0005-money-in-kopecks.md), [ADR 0006](../adr/0006-vat-rate-from-catalog.md).

**Строка**

1. Сумма = количество × цена, округлённая до копейки половиной вверх.
2. Ставка — число `Ставка` из справочника по `СтавкаНДС_Key` строки.
3. НДС от уже округлённой суммы строки:
   - `ЦенаВключаетНДС = false`: НДС = сумма × ставка / 100; сумма с НДС = сумма + НДС;
   - `ЦенаВключаетНДС = true`: НДС = сумма × ставка / (100 + ставка); сумма с НДС = сумма.
4. Отменённые строки (`Отменено = true`) в документ не входят.

**Итоги** — сумма округлённых значений строк, без пересчёта от общей суммы.

**Сверка с эталоном и данными базы** (зафиксировано тестами)

| Случай | Данные | Результат |
|---|---|---|
| Итоги 00ДМ-000101 | 4 строки, флаг снят | 21181 / 3210.82 / 24391.82 |
| «22/122» при снятом флаге | 2 × 990,50 | 1981 / 435.82 / 2416.82 |
| Флаг поднят | 00ДМ-000102: 4 × 2400, 22% | 9600 / 1731.15 / 9600 |
| Половина копейки | 00ДМ-000103: 5 × 1,15, 22% | 5.75 / 1.27 / 7.02 |
| Дробное количество | 00ДМ-000103: 0,125 × 8000 | 1000 |
| Нетиповая ставка | 1 × 15000, 13% | 15000 / 1950 / 16950 |
| НДС от округлённой суммы | 1 × 2,2451, 22% | сумма 2.25, НДС 0.50, а не 0.49 |
| Итог из строк | 2 строки по 0,25, 22% | НДС 0.12, а не 0.11 |

## 8. Данные получателя

Фамилия, имя, телефон и почта обязательны; отчество необязательно. Телефон нормализуется к `+7XXXXXXXXXX`. Пол берётся из `gender`, а при отсутствии определяется по отчеству; без обоих значений возвращается ошибка конкретного поля. Склонение выполняется по правилам Petrovich, PDF остаётся текстовым.

## 9. Тестирование

`go test ./...` проверяет доменные расчёты, OData-клиент (на подставных HTTP-ответах), PDF, сценарии и HTTP-контракт.

Live smoke против настоящей goshift.ru (13.09.2026, отдельный процесс на :3001, не мок): preview 00ДМ-000101 совпал с эталоном задания побайтово; суммы всех 5 заказов совпали с независимым ручным расчётом при разведке; PUT `shipment-draft` вызван дважды подряд — второй раз вернул тот же `ref`/`number` с `created:false`; сама 1С за время прогона несколько раз ответила `503`, клиент отретраил с нарастающей паузой и не отдал ни одной ошибки наружу.

## 10. Эксплуатация

Скопировать `.env.example` в `.env`, заполнить реальные параметры OData и выполнить `docker compose up --build`. Проверка готовности сервиса: `GET /healthz`. Состояние интеграции без лишнего вызова 1С: `GET /api/v1/status`.

## 11. Риски и неизвестные

База общая, поэтому в ней видны чужие реализации; сервис считает своим только документ с собственным маркером. Физический остаток не равен доступному к выдаче: резервы намеренно выводятся отдельно. Изменение OData-метаданных 1С потребует обновить DTO в `internal/infrastructure/onec`.

## 12. Осознанно не сделано

Нет пользовательской авторизации, истории выдач, базы данных приложения и отдельного расчёта «доступно» (остаток минус резервы). Эти функции не нужны для проверки задания и добавили бы состояние либо спорную бизнес-семантику.
