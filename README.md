# Выдача заказа клиенту

Тестовое задание GoShift: страница кладовщика поверх OData 1С:УТ 11.5. Кладовщик открывает заказ, видит его состав и реальный остаток на складе, вводит данные получателя, печатает документ на выдачу и отмечает выдачу в 1С черновиком реализации. Исходников и конфигуратора 1С нет — только чужая база, опубликованная по OData, с паролем из задания.

Колонка остатка — это физический остаток склада (`ТоварыНаСкладах`): отвечает на вопрос «сколько лежит на полке сейчас». Резервы других заказов показаны рядом отдельной колонкой и не вычитаются из остатка — иначе колонка на самом деле называлась бы «доступно к выдаче» и смешивала бы два разных понятия: что физически есть и что можно выдать без нарушения чужой брони.

## Стек

Go 1.26, без веб-фреймворка (`net/http` + `http.ServeMux` с паттернами методов). Из внешних зависимостей: `gopdf` для PDF, `sony/gobreaker` для размыкателя, `golang.org/x/time/rate` для лимита частоты запросов, `testify` в тестах. Фронтенд — один HTML-файл со встроенными JS/CSS без сборки.

## Запуск

Нужны Docker и Docker Compose.

```powershell
Copy-Item .env.example .env
# укажите в .env пароль из условия задания
docker compose up --build
```

Откройте [http://localhost:3000](http://localhost:3000). Сервис слушает порт 3000, а данные 1С читает по адресу, логину и паролю из окружения (`.env` не попадает в репозиторий).

Без Docker — `go run` не читает `.env` сам, переменные нужны в оболочке:

```powershell
$env:ONEC_BASE_URL = "https://goshift.ru/demo_ut/odata/standard.odata"
$env:ONEC_USER = "odata.user"
$env:ONEC_PASSWORD = "<пароль из задания>"
go run ./cmd/server
```

Есть `Makefile` с теми же командами (`run`, `test`, `lint`, `fmt`, `build`) — на Windows без `make` их проще запускать как в примерах выше.

## Структура проекта

```
cmd/server                  точка входа: конфигурация, сборка зависимостей, HTTP-сервер
internal/domain             доменная логика: money, vat, order, stock, person, pickup, shipment — без I/O
internal/usecase            контракт между транспортом и бизнес-логикой: порты, DTO, узкие интерфейсы (OrderCatalog, DocumentComposer, ShipmentRegistrar, StatusReporter)
internal/service            реализация usecase.API поверх портов
internal/infrastructure
  onec                      клиент OData 1С: повторы, размыкатель, лимит частоты, защита от блокировки учётки
  pdf                       рендер документа на выдачу в PDF (gopdf + вшитый PT Sans)
  petrovich                 склонение ФИО в родительный падеж по правилам проекта petrovich
internal/transport/httpapi  HTTP-хендлеры, DTO контракта задания, RFC 9457 problem+json
api                         OpenAPI-спецификация (api/openapi.yaml), встроенная в бинарник и отдаваемая по /api/v1/openapi.yaml
docs                        ADR, TDR, C4-диаграммы — подробности решений
```

В каждом пакете `internal` модели (структуры, типы, константы) отделены от их логики: `model.go` — что это такое, соседние файлы — что оно делает. HTTP-хендлеры зависят только от интерфейсов `usecase`, а не от конкретной реализации сервиса.

## API

- `GET /api/v1/orders` — список заказов для выбора;
- `GET /api/v1/orders/{orderRef}` — экран заказа: строки, остатки, подсказка получателя из последнего заказа клиента;
- `POST /api/documents/preview` (и `/api/v1/documents/preview`) — обязательный контракт задания, документ на выдачу как JSON;
- `POST /api/v1/documents/pdf` — тот же документ в текстовом PDF;
- `PUT /api/v1/orders/{orderRef}/shipment-draft` — создаёт черновик реализации в 1С (идемпотентно) и перечитывает его для сверки; `GET` того же пути — вернуть уже созданный черновик, не создавая новый;
- `GET /api/v1/status` — известное состояние связи с 1С (не делает запрос в 1С, только то, что уже знает клиент);
- `GET /healthz` — живость процесса.

Контракт целиком — `GET /api/v1/openapi.yaml`, интерактивно — `/swagger/`.

Запрос обязательного контракта:

```json
{"orderRef":"2da145f0-d5fc-11f1-a0b3-48df371887e9","customer":{"lastName":"Воронцов","firstName":"Пётр","middleName":"Аркадьевич","gender":"м","phone":"8 (999) 123-45-67","email":"p.vorontsov@example.com"}}
```

Ответ (поля `issuable`/`blockReasons` — сверх контракта задания, для страницы и проверяющего; денежные поля — числа, как в примере задания, а не строки):

```json
{
  "customer": {"fullNameGenitive": "Воронцова Петра Аркадьевича", "phone": "+79991234567", "email": "p.vorontsov@example.com"},
  "order": {"number": "00ДМ-000101", "date": "2026-09-01T00:00:00", "warehouse": "Центральный склад", "priceIncludesVat": false},
  "lines": [{"article": "...", "name": "...", "qty": 3, "price": 1250, "vatName": "22%", "amount": 3750, "vatAmount": 825, "amountWithVat": 4575}],
  "totals": {"amount": 21181, "vatAmount": 3210.82, "amountWithVat": 24391.82},
  "issuable": true,
  "blockReasons": []
}
```

## Бизнес-правила расчётов

Все суммы — в целых копейках, округление половины вверх (1.265 → 1.27, а не банковское округление до чётной). НДС считается от уже округлённой суммы строки, а не от точной; итог документа — сумма итогов строк, а не пересчёт от общей суммы. Ставка «добавить сверху» или «выделить из суммы» определяется флагом заказа `ЦенаВключаетНДС`, а не названием ставки — у одной и той же ставки «20%» цена может как включать, так и не включать налог в зависимости от заказа.

Имя получателя склоняется в родительный падеж («кого?»), с учётом пола: если `gender` не передан, он определяется по окончанию отчества. Правила — оригинальный JSON проекта petrovich, а не готовый Go-порт: у существующих портов есть ошибка (не останавливаются на первом подходящем правиле «оставить как есть»), из-за которой мужская фамилия «Седых» превращается в «Седыха».

## Надёжность и границы 1С

1С отдаёт данные маленькими страницами и не сообщает, что есть ещё, — клиент листает `$skip`, пока не придёт пустая страница, и останавливается, если 1С вернула ту же страницу дважды подряд. По условию задания около 1 из 30 запросов завершается временной ошибкой: клиент повторяет только безопасные операции (чтение, 429) с растущей паузой (1/2/4 с ±20%) и не повторяет POST вслепую — при неоднозначном исходе (503, обрыв) следующий цикл сначала ищет черновик в 1С, а не создаёт новый. После серии сбоев подряд размыкатель на время перестаёт слать запросы, чтобы не подсаживать и без того нестабильную базу.

Неверный пароль или блокировку учётки клиент запоминает и больше не пытается заново — по условию задания пять неудачных попыток блокируют учётку на пять минут для всех пользователей общей базы, и раз залогинившись подтверждённым паролем, повторно проверять его незачем.

Черновик реализации создаётся идемпотентно: перед POST сервис ищет уже существующий черновик по маркеру в комментарии (клиентский `Ref_Key` 1С игнорирует), а после записи перечитывает документ и сверяет с отправленным — код 201 сам по себе не значит, что записалось то же самое. Повторное нажатие «Отметить в 1С» не создаёт второй черновик.

Данные получателя (ФИО, телефон, почта) нигде не сохраняются и не попадают в черновик реализации — только в ответ конкретного запроса и в PDF.

## Что не сделано намеренно

Авторизация кладовщика, история выдач, полноценный учёт доступности (остаток минус все резервы, а не только показ рядом) и отдельная БД сервиса. Для тестового задания это добавило бы состояние и риски, не нужные выдаче через чужую 1С с общим для всех паролем.

## Тестирование

```powershell
go test ./...
```

Тесты разложены по тем же слоям, что и код: доменная логика проверяется без моков и I/O, `internal/service` — на подставных портах (`usecase/usecasetest`) с эталонными данными демо-базы (`domain/domaintest`), `internal/infrastructure/onec` — на встроенном HTTP-фикстуре, `internal/transport/httpapi` — на полном сервисе от HTTP-запроса до JSON-ответа, включая сверку с примером из задания. Денежные и НДС-расчёты проверены на всех пяти демо-заказах и сверены с эталоном задания вручную на живой базе.
